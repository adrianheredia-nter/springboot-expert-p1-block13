# Spring Boot Expert P1 - Block 13

REST API for insurance clients and their policies, built to practise testing across the different layers of a Spring Boot application.

## Stack

- Java 17, Spring Boot 3.2.5
- Spring Web, Spring Data JPA, Bean Validation
- H2 in-memory database
- Lombok 1.18.24
- JUnit 5, Mockito, MockMvc, Rest Assured, JaCoCo

## Running it

```bash
./mvnw spring-boot:run
```

The API listens on `http://localhost:8080`. The database is recreated on every start and loaded from `src/main/resources/data.sql` with two clients and three policies.

H2 console: `http://localhost:8080/h2-console` (JDBC URL `jdbc:h2:mem:insurance`, user `sa`, empty password).

## Domain

`ClientJPA` keeps the client data (`idClient`, `dni`, `name`, `surname`, `birthdate`) and a `@OneToMany` list of policies. `PolicyJPA` has an autogenerated `idPolicy`, `numPolicy`, `branch`, `subBranch` and the `@ManyToOne` owning client.

A few rules worth knowing:

- `idClient` is not generated, it comes in the request. Creating a client with an existing id returns 409.
- The DNI is normalised (trimmed, uppercase, no dash) and the control letter is checked. It must be unique.
- Policy numbers are unique. Deleting a client also deletes its policies.
- Dates use the `yyyy-MM-dd` format.

## Endpoints

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/clients` | List clients with their policies |
| GET | `/api/clients/{idClient}` | Get one client |
| GET | `/api/clients/{idClient}/policies` | Policies of a client |
| POST | `/api/clients` | Create a client |
| PUT | `/api/clients/{idClient}` | Update a client |
| DELETE | `/api/clients/{idClient}` | Delete a client and its policies |
| GET | `/api/policies` | List policies |
| GET | `/api/policies/{idPolicy}` | Get one policy |
| POST | `/api/policies` | Create a policy for an existing client |
| DELETE | `/api/policies/{idPolicy}` | Delete a policy |

Example:

```bash
curl -X POST http://localhost:8080/api/clients \
  -H "Content-Type: application/json" \
  -d '{"idClient": 3, "dni": "11111111H", "name": "Ana", "surname": "Lopez", "birthdate": "1992-01-15"}'

curl -X POST http://localhost:8080/api/policies \
  -H "Content-Type: application/json" \
  -d '{"numPolicy": "POL-0004", "branch": "car", "subBranch": "full", "idClient": 3}'
```

Errors come back as `{"timestamp", "status", "error", "message"}` with 400, 404 or 409.

## Tests

```bash
./mvnw clean verify
```

`verify` runs every test and fails the build if line coverage drops below 80%. The HTML report ends up in `target/site/jacoco/index.html`.

| Class | What it covers |
|-------|----------------|
| `InsuranceApiRestAssuredTest` | Full app on a random port, called with Rest Assured |
| `ClientControllerTest`, `PolicyControllerTest` | Controllers with MockMvc and mocked services, including error responses |
| `ClientServiceH2Test` | Real services and repositories against H2 (`@DataJpaTest`) |
| `ClientServiceImplTest`, `PolicyServiceImplTest` | Service logic with `@InjectMocks` and `@Mock`, create flows checked with `ArgumentCaptor` |
| `DniUtilsTest` | DNI normalisation and validation |

## SonarQube

The JaCoCo XML report path is already set in the pom, so after `verify` the analysis picks up coverage:

```bash
./mvnw clean verify org.sonarsource.scanner.maven:sonar-maven-plugin:sonar -Dsonar.host.url=<url> -Dsonar.token=<token>
```
